# 45. Проверяем запись в БД

[Открыть урок на сайте](https://palmekaprocode.ru/courses/qa-auto-javascript/lessons/database-js-changes)

## Зачем это нужно в автотесте

Статус успешного INSERT еще не доказывает, что сохранились нужные значения. Здесь добавим одну строку, прочитаем ее обратно и восстановим исходное состояние после проверки.

## Что уже надо знать и подготовить

Проверьте эти условия до запуска примера.

- Пройдите SELECT и JOIN. request, expect и SQL уже знакомы; здесь добавим finally к известной конструкции try/catch, чтобы очистка выполнилась даже при падении.
- Нужен отдельный аккаунт с доступом к тренировочному полю, которым не пользуются ученики и другие тесты. Команда reset сбросит все его учебные таблицы, поэтому общий test-auto@palmekaprocode.ru здесь не используйте.
- В терминале задайте export QA_EMAIL="почта_отдельного_аккаунта" и export QA_PASSWORD="пароль_отдельного_аккаунта". Setup из урока авторизации прочитает эти переменные и запишет его cookie в playwright/.auth/student.json.
- Перед запуском завершите другие тесты этого аккаунта. В одном запуске не смешивайте проверку INSERT с читающими тестами на том же аккаунте.

## Сначала разберем слова

Проверка записи в БД отличается от проверки чтения. Успешный статус INSERT еще не доказывает, что нужная строка сохранилась. После записи читаем ее по id и сравниваем столбцы с исходными данными.

- **INSERT**: добавляет строку, UPDATE меняет строку, DELETE удаляет ее.
- **Изменение**: данных называют мутацией. После него нужен повторный SELECT, чтобы проверить фактическое состояние.
- **Предусловие теста**: известная исходная база. Здесь ее дает action: reset на отдельном учебном аккаунте.
- **finally**: выполняет очистку даже тогда, когда ассерт внутри try упал.

## Как это работает

Для этого упражнения используйте отдельный тестовый аккаунт: reset восстанавливает все его личные учебные таблицы. Нельзя запускать такой тест в аккаунте, где другой ученик или другой тест сохраняет свои результаты. Прогресс задач после reset остается.

- Восстановить исходные учебные таблицы
- Выполнить INSERT одного покупателя
- Проверить changed и статус
- Прочитать покупателя через SELECT
- В finally восстановить исходный набор

## Файл tests/database/customer-insert.spec.js

Создайте tests/database/customer-insert.spec.js. Тест запускается только с флагом RUN_SQL_CHANGES=1 и проверяет, что выбрали отдельный аккаунт. Он делает по одному SQL-запросу за реквест и восстанавливает базу в finally.

[Открыть готовый файл](../tests/database/customer-insert.spec.js)

**Обратите внимание.** У SELECT с WHERE результат упражнения tables-customers может быть не засчитан: эта учебная задача ожидает все строки. Автотест здесь проверяет сохраненную запись через rows. Reset меняет весь личный набор, поэтому нужен отдельный аккаунт.

## Как запустить

Выполняйте шаги по порядку.

- Задайте QA_EMAIL и QA_PASSWORD отдельного аккаунта в текущем терминале. Не используйте общий test-auto@palmekaprocode.ru.
- В корне qa-playwright выполните RUN_SQL_CHANGES=1 npx playwright test tests/database/customer-insert.spec.js --project=chromium --reporter=list. Команда запускает именно эту спеку, не весь набор.

## Какой результат ожидать

При отдельном аккаунте и доступе к полю будет 2 passed: setup и тест записи. После INSERT changed равен true, SELECT возвращает покупателя 109, а finally удаляет изменение через reset. Обычный полный запуск без RUN_SQL_CHANGES=1 покажет этот тест как skipped.

```text
2 passed
```

## Что поменять для проверки понимания

Меняйте по одному пункту, сначала предскажите итог, потом запустите пример и верните исходную строку.

- Поменяйте только ожидаемый город в toEqual на "Москва". Проверка упадет, но finally все равно восстановит таблицы: итог 1 passed и 1 failed.
- Верните город и замените id в SELECT на 108. Вернется пустой массив, проверка строк упадет, очистка снова выполнится.
- Верните id 109 и запустите пример еще раз. Итог снова 2 passed: запись не осталась после первого запуска.
